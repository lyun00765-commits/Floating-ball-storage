# 基线评估（v1.0）

> **归档说明**：这是 v1.0→v1.1 重构**前**的历史评估（当时的问题清单与路线决策），
> 内容反映重构前状态，仅供溯源。当前状态见 `docs/03-交接与后续计划.md`。

评估对象：`src/index.js`（4132 行 / 190 KB），与 `dist/悬浮球收纳-v1.0.json` 的 `content` 逐字节一致。

---

## 一、结论

功能完整、可用，但**交付物是 webpack 打包产物，不是可维护源码**。局部变量已被统一混淆为 `e/t/n/a/o`，所有函数被平铺在一个模块作用域，状态用约 20 个模块级可变变量散落管理。这就是"打补丁堆成屎山"的技术根因：改动无法局部化，任何一次修改都要在 4000 行里靠 grep 定位。

重构是值得做的，而且空间很大。不会改变任何外部行为。

## 三、问题清单

严重度：**A** = 影响功能正确性；**B** = 性能/稳定性隐患；**C** = 兼容性/可维护性。

### A 类

| # | 问题 | 位置 |
|---|---|---|
| A1 | **两套互不一致的悬浮球识别规则**。手动捕获 `s()`：尺寸 16–160、宽高比 0.35–2.8；自动捕获 `isFloatingBallCandidate()`：尺寸 20–120、比值 0.6–1.7，且两处打分权重不同。同一个元素手动能捕、自动捕不到（或反之）。维护时改一处必漏另一处。 | L319 / L2925 |
| A2 | **主运行时 cleanup 不回收「输入框入口」**。二者是两套生命周期的 IIFE，`edgePanelRuntimeCleanup` 只清主面板；脚本被宿主移除时输入框按钮与 `mountObserver` 残留。 | L3363 / L3916+ |
| A3 | **`composeTransform` 会叠加 scale**。元素 transform 已含 `matrix(0.68,…)` 时再捕获/更新，结果为 `matrix(…) scale(…)`，球越缩越小。修复路径 `updateCapturedBallElement → G()` 可复现。 | L392 |
| A4 | **`toastr` 调用无保护**。捕获失败分支中 `toastr.*` 若抛错，后续 `exitCaptureMode()` 不执行，捕获遮罩卡死需刷新。全文件 12 处调用同样裸奔。 | L411–482 等 |

### B 类

| # | 问题 | 位置 |
|---|---|---|
| B1 | **位置刷新定时器风暴**。`edgePanelSchedulePositionRefresh` 一次排 8 个 timeout（0/80/220/480/820/1500/2600/4000 ms），而 `focusin`/`focusout` 都绑了它——每次输入框获焦/失焦各拉 8 个定时器。 | L2791 / L3300+ |
| B2 | **`Ze` 监听 body 全子树且不排除聊天区**。AI 流式输出时每次 DOM 变更（每 token）都执行 3 次 `querySelector`。旁边的 `Qe` 明确跳过了 `#chat`，`Ze` 漏了。 | L3296 |
| B3 | **兜底全量扫描代价高**。`querySelectorAll("button,div,span,a")` + 逐元素 `getComputedStyle`（强制样式计算），节流后约每 12 秒一轮，酒馆页面元素量级下是明显开销。 | L3019 |
| B4 | **属性子串选择器**：`[style*="position: fixed"]` 无法走索引，退化为全量属性扫描，与 B3 叠加。 | L3020 |
| B5 | `fbUpdateArrows` / 相关分页函数用 document 级全局查询 `[data-fb-page-prev]`，多实例会互相串。 | L660 |

### C 类

| # | 问题 | 位置 |
|---|---|---|
| C1 | 平台 API 硬耦合且**保护程度不一**：`getScriptId`/`getVariables`/`replaceVariables`/`z`/`Vue`/`toastr`/`$`/`klona`。其中 `$` 在主题色模块有保护（L1804），在 `ht()` 里没有——iframe 一旦无 jQuery，`ht()` 会**半初始化中断**（监听器与 cleanup 未注册），比直接报错更难排查。 | 多处 |
| C2 | CSS 使用 `:has()`（`#form_sheld:has(#send_textarea:focus)`），需 Chrome 105+ / Safari 15.4+。 | 注入样式 |
| C3 | `F()` 用 `Object.defineProperty` 覆盖 CSSStyleDeclaration 实例上的 `position/top/left/…` 访问器。Safari 下宿主对象行为可能不同，失败被 `try{}catch{}` 静默吞掉，表现为"样式保护失灵但无人知道"。 | L725 |
| C4 | `.prefault()` 依赖平台注入的 zod 版本（v4 语义）；无版本兜底。 | L1111 |
| C5 | 注释与实现不符：`info` 写"三种入口：边缘拉手/输入框按钮/**两者都显示**"，实现只有 `edge`/`input`/`longpress`，没有"两者都显示"。 | info 字段 / L3916+ |

### 不是问题的部分

- `At` 集合不构成泄漏：`removeCapturedBall → onBallReleased` 会同步删除（L1598）。
- `WebSocket`/存储等无隐患。
- 分页、指纹匹配、主题同步逻辑本身设计合理，值得保留。

## 四、重构路线（待定）

| 路线 | 做法 | 代价 |
|---|---|---|
| **1. 拆源 + 自建构建链** | 以现有 bundle 为唯一真相，拆成多文件 ESM（识别/接管/存储/面板/入口），用 esbuild 打包为单文件 → 注入 JSON。可去 webpack 样板与混淆变量，代码量预计降 30–40% | 引入 node 构建依赖；需确认酒馆对单文件产物的要求 |
| **2. 单文件就地重构** | 保持单文件手写，分节 + 重命名 + 去重 + 修复 | 改动可控，但 4000 行单文件的可维护性上限不高 |
| **3. 仅修 bug** | 不做结构重构 | 技术债保留，后续每次改动仍痛苦 |

**倾向路线 1。** 理由：交付物最终必须是单文件，但"单文件"是构建结果，不该是开发形态；路线 2 会让下一次重构再来一遍。

无论哪条路线，建议顺序一致：先建立**可回归验证的手段**（否则 4000 行重构 = 盲改），再按 A → B → C 逐项推进，每项单独提交。
