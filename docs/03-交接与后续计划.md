## 三、工作方法（每批照做）

1. **改语义名**：`node scripts/rename-symbols.mjs <file> OLD=NEW ...`
   —— 作用域感知，禁止文本替换
2. **算依赖闭包**：`/workspace/3_sandbox/deps.mjs <函数名>...`（找跨块引用的顶层声明）
3. **抽取**：写一次性脚本放 `/workspace/3_sandbox/`，
   **用 espree 的 AST `range` 精确切分**（不要用字符串 marker——曾把相邻函数切坏）
4. **补 import / 改引用点**：`npm run lint` 的 `no-undef` 会暴露悬空引用
5. **四道检查**：`npm run check`（语法+依赖图）→ `lint` → `verify` → `build`
   —— `check` 用 esbuild，能校验具名导出；lint 不能。两者互补，**都必须跑**
6. **建 parity 规格** → `npm run verify`
7. **独立提交**；**回查模块对外导出**（见坑 12）

### 验证的三个层次

| 层次 | 适用 | 工具 |
|---|---|---|
| 逐字节比对 | 纯搬运（首选） | `scripts/parity/*.json` + `npm run verify` |
| token 级比对 | 有依赖注入/状态私有化等「有意改写」 | `/workspace/3_sandbox/verify-*.mjs`：对基线施加同一套改写后比 token 序列 |
| 人工确认 | 无法机械比对的 | 逐处核对并记录差异行 |

**`rewrites`（规格内的有意改写登记）**：当重构不只是搬运（抽共享常量、补缺陷等），
逐字节比对必然失败。此时在规格里写 `rewrites: { 函数名: [{desc, find, replace}] }`，
工具会**先对基线函数体施加同样的改写再比对**。改写会被打印在结果里
（`（施加了 N 处已登记的有意改写）`），所以它必须是被审阅过的、可复现的，
而不是用一句"已知差异"糊过去。**行为变更也要走这条路并写进 desc**，例如
candidate 补关闭按钮排除那次。

token 级比对的做法：先对基线区间施加与抽取脚本**完全相同**的改写规则，再与模块比对。
规则要写到完全对齐为止（scanner 那次写到第 5 条才对齐）——**一旦对齐，说明搬运是纯粹的**。

## 六、关键设计决策

- **状态跟着函数走**：迁「状态 + 操作它的函数」整簇，不抽公共 state。
- **释放记忆只在自动模式下生效**（有意设计，勿当 bug 修）：自动扫描是后台行为，
  必须尊重「用户已表示不要」的记忆；手动模式下的长按一键捕获是用户主动发起的明确操作，
  语义是「能收的都收进来」，此时跳过释放过的球反而让用户困惑。
  代码在 `capture/candidate.js` 有同样说明。
- **`clickCapturedBall` 只处理 `root-open` 类型**：点击已收纳的球时，只有
  `ai-floating-panel-*` 这类球会被打开面板（`takeover.js` 只给它们绑了 click 监听）。
  同函数内原本还有个 `default` 分支（模拟点击、把球取出后再收回），但它依赖的前提
  从未成立（该分支的调用方不存在），且其中把 `Vue` 对象当 DOM 元素用。
  已作为死代码删除（`store.js` 减少 54 行）。
- **对外只暴露能力**：如分页模块导出 `appendBall`，不暴露 `pageLayer`。
- **依赖倒置处理循环依赖**：模块永不反向 import 装配层。
  - scanner ↔ store：store 单向 import scanner；scanner 用 `setScanDeps({ store })` 注入。
  - guards → store：`setViewportGuardDeps({ togglePanel, getPanelPositionTarget })`。
  - view → store：`setViewDeps({ store, triggerScan })`。
- **`index.js` 的对外导出是契约**：`export { tryCaptureBall as captureElement, store as pluginStore, ... }`
  —— 被外部脚本调用，改名时必须同步，否则使用方拿不到接口。
- **平台契约**（宿主 iframe 注入，不参与打包，eslint 白名单）：
  `Vue` `$` `toastr` `z` `getScriptId` `getVariables` `replaceVariables`
- **产物不提交**：`build/` 在 gitignore；确认稳定后人工拷入 `dist/`。

## 七、踩过的坑（按发现顺序）

1. **边界抽多**：按 `const Ne = {` 取上界，误删了它前面的 store 状态 → 94 个 lint error。
   **定界前先 grep 区间内的顶层声明清单。**
2. **用 AST 切边界，不要用字符串 marker**：要「抽一整段但剔除中间某几个函数」时，
   字符串切片会把相邻函数切坏。
3. **同一条 const 链**：`const A = {...}, B = ..., C = ...` 是**一个**声明语句。
   拆链写法：`},\n  B = ` → `}\nconst B = `。
4. **对象方法的缩进**是 4 格（不是 2 格）。
5. **短名重命名必须作用域感知**：`j` 全文件 8 处只有 4 处指向目标函数。
6. **基线里已包含上一批的重命名**，spec 的 `rename` 只写本批新做的改名。
7. **eslint 的 `no-undef` 是搬移期最重要的防线**，但**不校验具名导入是否存在**——
   那条由 `npm run check`（esbuild）兜住。
8. **`export const a = 1, b = 2` 里的 `b` 是导出的**（曾误判为不导出）。
9. **`;((A = !0), X, Y))` 这类链很脆**：把首项换成 `fn()` 时，`fn()` 会"吃掉"原来
   闭合内层括号的 `)`；删掉链中间的项后，链尾的 `))` 会变悬空。
   报错行号指向**后续语句**，不是真正的问题位置。
10. **JS 的 `String.replace(字符串, x)` 只替换第一处**（Python 的 `str.replace` 是全部）。
    写核对脚本时踩过，导致"替换后仍不一致"的假差异。用 `replaceAll` 或带 `g` 的正则。
11. **`str.replace('lt =', ...)` 这类子串替换会误伤 `glt =`**（`g` + `lt =`），
    造出 `gscanTimer` 这种怪名字。短名批量替换必须带标识符边界。
12. **搬完要回查模块对外提供的名字是否与调用点一致**：`gt`/`Ct`/`ft` 改名后，
    文件末尾的 `export { gt as captureElement, ... }` 立刻失效——这是运行时契约。
13. **不要用正则改短名**：抽 store 时用 `o.` → `Vue.` 的正则，误伤了局部变量
    （`o` 在那里是元素不是 Vue）。**必须用 rename-symbols.mjs（作用域感知）**。
14. **替换「逗号表达式链」中的一环时，要看清这一环占了多少括号**：
    `;(!(function (e) {...})({...}), ...)` 里 `;(` 是**整条链的开始**，
    替换掉这个环时若把 `;(` 一起删掉，链尾的 `)` 就悬空了（我踩过两次）。
    另一侧的坑：`re.match(/\s*,/)` 把环后的逗号也算进替换范围，
    结果环之间少了逗号 → `Unexpected token`。
    **替换后立刻跑 `npm run lint`（语法错误会直接报 Parsing error）。**
15. **核对脚本自身的两个坑**：
    ① 项目 `package.json` 有 `"type": "module"`，临时脚本若用 `require` 必须叫 `.cjs`；
    ② `node script.js ARG` 里脚本路径占 `argv[1]`，**参数是 `argv[2]`**；
    ③ 临时脚本要放在**项目目录内**（否则找不到 `node_modules/espree`）。
16. **注入未接通会静默失效**：`deps` 有安全默认值时，lint/build 都不报错，
    但运行时拿到空 store。抽完带注入的模块立刻接注入并回查。
